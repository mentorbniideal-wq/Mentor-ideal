# Monthly History backfill

The existing Monthly Sync remains the operational current-period import. The dedicated Monthly History page is in the Mentor Desktop system/admin navigation, not the Growth workspace or the Monthly Sync modal. It shows ten reporting periods at a time and accepts only the month-addressable Member Traffic Light CSV for one past period. Reporting2You and Traffic Lights Evolution are available only as of the BNI login/download date; they must not be attached to a historical reporting month. The page previews stable-member matching and verifies the month printed in the MTL report before explicit confirmation. It never calls the operational Monthly Sync action.

Historical backfill writes only Member Traffic Light rows in `member_performance_source_snapshots` and its existing `monthly_sync_batches` ledger and audit event. It does not write current member details, current score, renewals, or operational counters. Source cells retain zero versus blank as zero versus null. Re-importing a period updates its MTL source snapshots by `(chapter_id, member_id, period_year, period_month, source_type)`, while retaining the old batch metadata and pre-import rows in `before_snapshot`. Growth trusts a completed MTL-only batch only for its MTL rows and labels the period `MTL_ONLY`, not three-source complete. Existing operational three-file batches retain their existing complete/partial rules. An incomplete or failed import is not trusted.

Both actions require an authenticated Google OAuth System Owner or Chapter Admin with the existing Monthly Sync execute capability; chapter scope comes from the server. The Mentor Desktop navigation and page are hidden from other roles, but backend authorization is authoritative. The preview expires after 30 minutes. Archived members with retained `members` records still match their stable ID. Rows with no unique member ID are excluded automatically from the imported snapshot, not assigned a fabricated identity; their count is stored in the batch/audit, while names are shown only transiently to the admin during preview. This exclusion does not independently prove the person dropped, so the UI says "unlinked" rather than "dropped". An entirely unmatched file and ambiguous same-name matches fail closed. Duplicate rows, missing MTL, extra Reporting2You/Evolution payloads, and a missing or mismatched month in the MTL report also fail closed. Report values remain raw source snapshots, never labeled monthly activity.

This workflow uses existing tables and needs no migration. It is intentionally not a database transaction across the batch ledger, audit event, and snapshot upsert. A failure marks the batch failed and the period untrusted; review the batch before retrying. No automatic rollback or deletion of historical records is provided. The new grid uses existing theme tokens and responsive rules; keyboard focus, loading, empty, error, preview, confirmation, and success states are included.
